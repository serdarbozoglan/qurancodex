BÖLÜM 01 · VİZYON
SECTION 01 · VISION

Vizyon

Vision

QuranCodex Semantik Concierge, kullanıcının doğal dilde sorduğu bir Kur'anî soruya halisinasyon üretmeden, yalnızca sitedeki gerçek ayet, tefsir, kavram, kıssa ve makaleleri seçerek yanıt veren bir RAG (Retrieval Augmented Generation) sistemidir. Kur'an metnini yorumlamaz, sadece ilgili kaynakları curate eder — kullanıcıyı okumaya, düşünmeye ve keşfetmeye yönlendirir.

QuranCodex Semantic Concierge is a RAG (Retrieval Augmented Generation) system that answers Kur'anic questions in natural language by selecting only real verses, tafsirs, concepts, stories, and articles from the site — never hallucinating. It does not interpret Kur'an; it curates relevant sources — guiding the user toward reading, reflection, and discovery.

Temel İlkeler

Core Principles

  • Halisinasyon YASAK — LLM sadece verilen aday havuzundan seçim yapar, uydurma id kullanamaz. Hydrate katmanında ID doğrulaması yapılır.
  • Yorum YASAK — LLM ayet üzerine tefsir yazamaz; sadece "bu ayet neden ilgili" cümlesi ekler.
  • Kur'an metnine dokunma — Arapça asla generate edilmez, veri kaynağından aynen okunur.
  • Kaynak-şeffaf — her sonuç kartında kaynak referansı (Suat Yıldırım, Elmalılı, Sahih International, vb.) net gösterilir.
  • Kendi kendini iyileştiren — kullanıcı feedback'i retrieval sıralamasını dinamik olarak değiştirir.
  • NO Hallucination — LLM only selects from provided candidate pool; fabricated IDs are rejected by the hydrate layer.
  • NO Interpretation — LLM cannot write tafsir on a verse; it only adds "why this verse is relevant".
  • Don't touch Qur'an text — Arabic is never generated; read verbatim from source data.
  • Source-transparent — every result card shows explicit source attribution (Suat Yıldırım, Elmalılı, Sahih International, etc.).
  • Self-improving — user feedback dynamically reshapes retrieval ranking.

Neden Bu Kadar Çok Katman?

Why So Many Layers?

Tek bir "her şey aynı chunk türünde" yaklaşımı belirli sorgu tipleri için zayıf recall verir. Örnekler:

A monolithic "everything as verses" approach gives poor recall for certain query types. Examples:

  • "Ashab-ı Kehf mağara hikayesi" → tek ayet match'i eksik kalır; pericope katmanı Kehf 18:9-26 bloğuna hedefli hit verir.
  • "Yasin suresi ne anlatır" → tek ayet 36:1 yeterli değil; sure özet katmanı 36'nın tam profili döner.
  • "faiz konusunda Elmalılı ne der" → verse match olur ama tefsir katmanı direkt Elmalılı 2:275 tefsir metnini getirir.
  • "Musa'nın Firavun'la karşılaşması" → 30+ ayet dağınık; kıssa scene katmanı "Musa'nın Büyücülerle Karşılaşması" sahnesini hedefli döner.
  • "Kur'an okuma prensipleri" → makale parent uzun; article-section katmanı "Epistemik Prensipler" bölümünü izole eder.
  • "Companions of the Cave story" → single-verse match falls short; pericope layer directly hits Kahf 18:9-26 block.
  • "What does Yasin surah discuss" → 36:1 alone insufficient; surah summary layer returns 36's full profile.
  • "What does Elmalılı say about interest (riba)" → verse matches but the tafsir layer directly returns Elmalılı's commentary on 2:275.
  • "Moses meeting Pharaoh" → 30+ scattered verses; kissa scene layer targets "Moses vs. Magicians" scene.
  • "Qur'an reading principles" → parent article is long; article-section layer isolates "Epistemic Principles" section.

Retrieval Pipeline Detayı

Retrieval Pipeline Detail

Adım 1 — Embed

Step 1 — Embed

Query, BGE-M3 (BAAI multilingual, 1024-dim) modeli ile embed edilir. DeepInfra API'si üzerinden batch-uyumlu; single query için ~300-500 ms. L2-normalize edilir, cosine similarity direkt dot product ile hesaplanır.

The query is embedded via BGE-M3 (BAAI multilingual, 1024-dim) through DeepInfra's API. ~300-500 ms per single query. L2-normalized, so cosine similarity is a simple dot product. 

// next/src/lib/concierge-embed.js
export async function embedQuery(text) {
  const res = await fetch('https://api.deepinfra.com/v1/inference/BAAI/bge-m3', {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${API_KEY}` },
    body: JSON.stringify({ inputs: [text] }),
  });
  const { embeddings } = await res.json();
  return new Float32Array(embeddings[0]);
}

Adım 2 — Cosine Search

Step 2 — Cosine Search

Corpus (corpus-embeddings.json) module-level cache olarak RAM'de tutulur (~180 MB). Her item için query ile dot product hesaplanır. Verse item'lar multi-vector — 3 embed'ten MAX seçilir.

The corpus (corpus-embeddings.json) is held in RAM as a module-level cache (~180 MB). Dot product computed against every item. Verse items are multi-vector — MAX over the 3 embeddings. 

function maxDot(queryEmb, embArr) {
  let max = -Infinity;
  for (const emb of embArr) {
    const s = dotProduct(queryEmb, emb);
    if (s > max) max = s;
  }
  return max;
}

Filtre: minScore 0.35 altındakiler drop edilir. Per-type kota uygulanır — verse 3, tefsir 2, article 2, article-section 2, kissa-scene 2, surah-summary 2, pericope 2, atlas × 5 tür × 1 = toplam 22 aday.

Filter: minScore 0.35 threshold drops weak matches. Per-type quotas — verse 3, tafsir 2, article 2, article-section 2, kissa-scene 2, surah-summary 2, pericope 2, atlases × 5 types × 1 = 22 candidates total.

Adım 3 — Feedback-Based Quality Boost

Step 3 — Feedback-Based Quality Boost

Top-N adayın item ID'leri KV'den quality score için batch fetch edilir (mget). Cold start protection: feedback < 20 olanlarda quality = 0.5 (no effect). Diğerlerinde:

Top-N candidates' item IDs are batch-fetched from KV for quality scores (mget). Cold start protection: feedback < 20 → quality = 0.5 (no effect). Otherwise: 

// Bayesian smoothing: prior 3 up + 3 down
quality = (up + 3) / (up + down + 6)

// Reranking multiplier
final_score = cosine × (1 + 0.3 × (quality − 0.5))
// quality 1.0 → cosine × 1.15 (max boost)
// quality 0.5 → cosine (nötr)
// quality 0.0 → cosine × 0.85 (max demote)

Adım 5 — Hydrate (halisinasyon guard)

Step 5 — Hydrate (hallucination guard)

Claude'un döndürdüğü her ID, corpus byId map'inde aranır. Bulunmayan (uydurulmuş) ID REJECT edilir + log warning. Bulunanlar için tam item detayları (Arapça metin, meal, url, vb.) response'a eklenir.

Every ID returned by Claude is looked up in the corpus byId map. Missing (fabricated) IDs are REJECTed + logged as warnings. Found items get their full details (Arabic text, meal, url, etc.) hydrated into the response.

3-Katmanlı Adaptive Guardrails

3-Layer Adaptive Guardrails

Sistem, kötü niyetli / bağlam dışı sorguları erken durdurmak için 3 katmanlı bir filtreye sahiptir. Katmanlar adaptive: temiz sorgular hemen geçer (~%80), sadece belirsiz/flag'li sorgular LLM katmanına iner (~%20).

The system uses a 3-layer filter to stop malicious/off-topic queries early. Layers are adaptive: clean queries fast-track (~80%), only ambiguous/flagged queries reach the LLM layer (~20%).

K1 — Regex Prefilter

K1 — Regex Prefilter

Deterministik pattern matching, sıfır cost, ~5 ms. 3 kategori:

Deterministic pattern matching, zero cost, ~5 ms. 3 categories:

  • Prompt injection (~10 pattern) — "ignore previous instructions", "act as", "<script>", "DAN mode", vb. → REJECT
  • Direkt hakaret (~15 pattern) — bağlamsız TR + EN küfür → REJECT
  • Fetva pattern (~6 pattern) — "caiz mi", "helal mi", "is X permissible", vb. → FETVA_TALEBI (retrieval devam, response'a disclaimer)
  • Prompt injection (~10 patterns) — "ignore previous instructions", "act as", "<script>", "DAN mode", etc. → REJECT
  • Direct abuse (~15 patterns) — context-free TR + EN profanity → REJECT
  • Fetva patterns (~6 patterns) — "caiz mi", "helal mi", "is X permissible", etc. → FETVA_TALEBI (retrieval continues, response gets a disclaimer)
Kritik Karar
Critical Decision

System Prompt Disiplini

System Prompt Discipline

  1. Verilen adaylar DIŞINDA ayet, sayfa, makale ÜRETME. Halüsinasyon YASAK.
  2. Ayete kendi TEFSİR yorumunu KATMA. "Bu ayette Allah şunu diyor..." gibi yorumlar YASAK.
  3. Ayet metni değiştirme, paraphraze etme. Adaydaki metin aynen kullanılır (referans ile).
  4. Sorulan konuya en uygun 3 ayet, 2-3 sayfa, 1-2 tefekkür seç (adaylardan). Uygunsa daha az seç.
  5. Her seçim için 1 cümlelik reason ekle — o item'ın soruya nasıl bağlandığını NEUTRAL şekilde açıkla.
  6. Yanıt DAİMA valid JSON — belirlenen şemaya göre.
  7. Adaylar yetersizse boş liste dön — uydurma.
  1. DO NOT generate verses, pages, or articles OUTSIDE the provided candidates. Hallucination FORBIDDEN.
  2. DO NOT add your own EXEGESIS. Comments like "This verse means..." are FORBIDDEN.
  3. DO NOT rewrite or paraphrase verse text. Use candidate text as-is (with reference).
  4. Select 3 most relevant verses, 2-3 pages, 1-2 articles (from candidates). Fewer is fine if less relevant.
  5. Include 1-sentence reason for each selection — neutrally explain how it relates to the query.
  6. Response MUST be valid JSON per the schema.
  7. If candidates are insufficient, return empty lists — never fabricate.

  • JSON output güvenli — Haiku strict schema takip eder.
  • Cheap — $0.25/M input, $1.25/M output. ~$0.001-0.002 per query.

İki Katmanlı Response Cache

Two-Layer Response Cache

Aynı sorgu farklı zamanlarda, farklı kullanıcılardan gelebilir. Sistem 2 katmanlı cache tutar:

The same query may arrive from different users at different times. The system maintains 2 cache layers:

Katman Layer Kapsam Scope TTL Amaç Purpose
Client localStorage 24h Aynı user, aynı browser — refresh/bookmark HIT Same user, same browser — refresh/bookmark HIT
Server Vercel KV (Redis) 7d Cross-user paylaşım — herhangi biri aynı soruyu ilk kez sordu mu? Cross-user shared — has anyone else asked this?

Cache Key

Cache Key

Deterministik SHA-256 hash — normalize edilmiş (lowercase, trim, whitespace collapse) query + lang:

Deterministic SHA-256 hash — normalized (lowercase, trim, whitespace collapse) query + lang: 

function computeQueryHash(query, lang) {
  const normalized = query.toLowerCase().trim().replace(/\s+/g, ' ');
  return crypto.createHash('sha256')
    .update(`${normalized}|${lang}`)
    .digest('hex')
    .slice(0, 16);
}

Cache Kuralları

Cache Rules

  • Sadece ok + fetva_talebi kategorilerinde başarılı response cache'lenir.
  • rewrite, reject, off_topic — cache'lenmez (dynamic content).
  • Server cache TTL 7 gün — corpus/prompt update sonrası doğal invalidation.
  • Admin panel'de "Tümünü Temizle" butonu ile manuel purge mümkün.
  • Only successful ok + fetva_talebi responses are cached.
  • rewrite, reject, off_topic — not cached (dynamic content).
  • Server cache TTL 7 days — natural invalidation after corpus/prompt updates.
  • Admin panel "Purge All" button for manual invalidation.

Kullanıcı thumbs up/down verdikçe sistem kendi kendini iyileştirir. Feedback şu üç noktayı besler:

As users give thumbs up/down, the system improves itself. Feedback drives three loops:

Faz 1 — Storage (KV)

Phase 1 — Storage (KV)

Her thumbs click /api/concierge/feedback'e POST edilir. Rate limit (60/dk/IP), input validation, localStorage dedup (aynı user aynı item'a 2. kez oy veremez). Server KV'ye 3 kayıt yazar:

Every thumbs click POSTs to /api/concierge/feedback. Rate limit (60/min/IP), input validation, localStorage dedup (same user can't vote twice on the same item). The server writes 3 KV records: 

// 1. Raw log
feedback:{timestamp} → { queryHash, itemId, thumb: 'up'|'down', lang, ipHash }

// 2. Query aggregate güncellemesi

// 3. Item aggregate (Faz 3 için)
item:{itemId} → { up, down, lastUpdated }

Faz 2 — Query Cache Curation

Phase 2 — Query Cache Curation

Server-side response cache — cross-user paylaşımlı, 7 gün TTL. Popüler soruların LLM cost'unu düşürür + speed 100× artırır. Ayrıca kullanıcı feedback'i cache'in kalitesini denetler:

Server-side response cache — cross-user shared, 7-day TTL. Reduces LLM cost for popular queries + speeds up 100×. User feedback also gates cache quality:

  • Positive %70+ → cache freeze (bu response güvenilir, TTL uzatılır — Faz 4 plan).
  • Negative %50+ → cache invalidate (bu response kötü, yeniden generate — Faz 4 plan).
  • Positive ≥70% → freeze cache (response is trusted, TTL extended — Phase 4 planned).
  • Negative ≥50% → invalidate cache (response is bad, regenerate — Phase 4 planned).

Faz 3 — Item Boost/Demote (Retrieval Reranking)

Phase 3 — Item Boost/Demote (Retrieval Reranking)

Her retrieval'da top-N candidate için item quality skoru KV'den fetch edilir. Feedback ≥ 20 olan itemler Bayesian smoothing ile skorlanır:

For each retrieval, top-N candidates' item quality scores are fetched from KV. Items with ≥20 feedback are scored via Bayesian smoothing: 

// Prior: 3 up + 3 down (nötr baseline)
quality = (up + 3) / (up + down + 6)

// Reranking multiplier
final_score = cosine × (1 + 0.3 × (quality − 0.5))

// Örnekler:
quality = 1.0 (all up)    → final = cosine × 1.15   (+15% boost)
quality = 0.75           → final = cosine × 1.075  (+7.5% boost)
quality = 0.5 (dengeli)   → final = cosine        (nötr)
quality = 0.25           → final = cosine × 0.925  (-7.5% demote)
quality = 0.0 (all down)  → final = cosine × 0.85   (-15% demote)

Cold start protection: feedback < 20 olanlarda quality = 0.5 kabul edilir (retrieval'a hiç etki etmez). Böylece yeni kartlar unfairly demote edilmez.

Cold start protection: items with feedback < 20 use quality = 0.5 (no retrieval effect). This prevents new items from being unfairly demoted.
